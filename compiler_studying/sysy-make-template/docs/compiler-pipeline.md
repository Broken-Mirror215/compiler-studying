# 从当前代码理解编译器的前端、中端和后端

本文基于 Lab9 结项版本 `lab9-complete`（`9799d2e`），解释各阶段在本项目中的实际位置。文中的代码路径相对于编译器项目目录，行号对应该版本。

当前实现已经包含前端和 RISC-V 后端，尚未实现独立的 IR 优化中端。`AST/BaseAst.h` 同时保存 AST 结构、符号管理、部分语义检查和 Koopa IR 生成逻辑；`src/main.cpp` 同时包含编译流程控制和 RISC-V 代码生成。理解阶段时，应关注代码接收和产生的表示，以及它承担的职责。

## 1. 先找到实际的编译流程

```mermaid
flowchart LR
    A["SysY 源码"] --> B["词法与语法分析<br/>sysy.l / sysy.y"]
    B --> C["AST"]
    C --> D["符号处理、检查、IR 生成<br/>BaseAst.h"]
    D --> E["Koopa IR 文本"]
    E --> F["libkoopa 解析<br/>构建 raw IR"]
    F --> G["RISC-V 代码生成<br/>GenRiscV"]
    G --> H["汇编"]
```

在 [main.cpp 的 main()](../src/main.cpp#L472) 中，可以沿下表追踪：

| 调用或操作 | 当前行号 | 输入 → 输出 | 作用 |
| --- | --- | --- | --- |
| `yyparse(ast)` | 485 | SysY 源码 → AST | 生成的 parser 调用 lexer，按照语法规则建立 AST |
| `ast->Dump()` | 501 | AST → Koopa 文本 | 遍历 AST，处理名字和部分语义约束，生成 IR |
| `koopa_parse_from_string()` | 506 | Koopa 文本 → Koopa 程序对象 | 解析并检查生成的 IR |
| `koopa_build_raw_program()` | 514 | Koopa 程序对象 → raw IR | 构建 C/C++ 后端方便遍历的数据结构 |
| `GenRiscV(raw)` | 538 | raw IR → RISC-V 汇编 | 分配栈空间，把 IR 操作落实为目标指令 |

`main()` 还负责打开输入、选择输出模式、处理输出文件和管理 Koopa 对象的生命周期。这些属于编译器驱动工作。

当前即使选择 `-koopa`，也会先经过 libkoopa 解析；随后输出原先生成的 Koopa 文本。选择 `-riscv` 时才调用 `GenRiscV()`。

## 2. 前端：理解源程序并生成 IR

前端要回答：源程序写了什么，名字指向哪个声明，哪些用法符合当前支持的语义，以及如何把这些行为表达成 IR。

| 前端工作 | 本项目中的位置 | 例子 |
| --- | --- | --- |
| 词法分析 | [src/sysy.l](../src/sysy.l) | 把 `int`、`x`、`3`、`+` 等识别为 token |
| 语法分析、构造 AST | [src/sysy.y](../src/sysy.y) | 判断 token 能否组成函数、声明和表达式，创建相应节点 |
| 名字和作用域处理 | [BaseAst.h 中的符号表](../AST/BaseAst.h#L35) | 登记 `x`、查找最近一层作用域中的 `x` |
| 编译期求值和部分语义检查 | `Calc()`、`CalcArrayDims()`、各节点的检查逻辑 | 求常量表达式、检查数组维数和是否允许赋值 |
| Koopa IR 生成 | 各节点的 `Dump()` 及输出辅助函数 | 生成 `alloc`、`store`、`load`、`add`、`br`、`call` 等 |

`sysy.l`、`sysy.y` 是 lexer/parser 的规则文件。Flex 和 Bison 根据它们生成 C++ 实现，因此 `yyparse()` 的实现不需要手写在 `main.cpp` 中。

当前语义检查与 IR 生成有相当一部分交织在 `Dump()` 中，并没有单独执行一个完整的语义分析遍历。

### 用一个源程序追踪前端

```c
int main() {
    int x = 3;
    return x + 2;
}
```

AST 中保留的是源程序的结构，例如：

```text
CompUnitAst
└── FuncDefAst: main
    └── BlockAst
        ├── VarDeclAst
        │   └── VarDefAst: x，初值为 NumberAst(3)
        └── StmtAst: return
            └── BinaryExpAst: +
                ├── LValAst: x
                └── NumberAst(2)
```

生成 IR 时，变量定义节点为 `x` 分配存储空间，并记录名字与地址的关系；名字引用节点查表取得地址；加法节点生成 `add`；返回节点生成 `ret`。

下面是简化临时变量命名后的 IR 示意，省略了本项目统一输出的库函数声明：

```koopa
fun @main(): i32 {
%entry:
    %x = alloc i32
    store 3, %x
    %v = load %x
    %sum = add %v, 2
    ret %sum
}
```

这里的 `Dump()` 已经是 IR 生成方法，而不是早期练习中打印 AST 结构的方法。名字沿用了下来，但方法的职责已经扩展。

## 3. 中端：分析和变换已经生成的 IR

中端常见的工作包括常量传播、常量折叠、删除无用指令、简化控制流和循环优化。它通常接收 IR，分析后再产生语义等价的 IR。

对上面的程序，经过合适的常量传播与无用代码删除后，可以得到：

```koopa
fun @main(): i32 {
%entry:
    ret 5
}
```

这是说明优化作用的示例，本项目当前没有实现将前一段 IR 自动变成后一段 IR 的优化 Pass。

### 有 IR，并不代表已经有独立的优化中端

`koopa_parse_from_string()` 和 `koopa_build_raw_program()` 负责解析 IR 和提供可遍历的数据结构。本项目没有在这两个调用之后执行一组自己的 IR 分析、变换 Pass。

可以把当前边界理解为：

```text
当前：前端生成 Koopa → libkoopa 构建表示 → 后端生成汇编
以后加入优化：前端生成 Koopa → IR 分析与变换 → 后端生成汇编
```

将来做中端优化时，还需要决定使用哪种可修改的 IR 表示和接口；不能仅仅因为拿到了 raw IR，就假设已经具备完整的优化框架。

### `Calc()` 属于当前的哪一阶段？

本项目中的 `Calc()` 主要对源程序里的常量表达式求值，例如数组长度、标量常量或要求在编译期确定的初值。它读取 AST 和符号信息，因此放在当前前端的编译期处理逻辑中理解更直接。

“在编译期算出一个数”这一行为也可以出现在中端，但判断当前代码的位置，要看它处理的是 AST 表达式还是已经生成的 IR 指令。

## 4. 后端：把 IR 操作落实到 RISC-V

后端接收 raw IR 中的函数、基本块、指令和类型，决定怎样用 RISC-V 指令、寄存器和栈空间实现它们。

| 后端问题 | 当前代码位置 | 实际工作 |
| --- | --- | --- |
| 一个对象占多少字节？ | [TypeSize()](../src/main.cpp#L27) | 在当前 RV32 目标上计算整数、指针和数组的大小 |
| 局部对象与临时结果放在哪里？ | [BuildStackFrame()](../src/main.cpp#L69) | 分配栈槽、预留调用参数区及返回地址保存位置 |
| 如何取得值或地址？ | [LoadAddress()](../src/main.cpp#L42)、[LoadValue()](../src/main.cpp#L174) | 区分立即数、全局符号、局部对象地址和已保存在栈中的结果 |
| IR 指令对应什么汇编？ | [GenRiscV()](../src/main.cpp#L229) | 遍历 IR，在 `switch` 的分支中生成算术、访存、分支和调用指令 |
| 如何进入和退出函数？ | `GenRiscV()` 的函数入口与返回处理 | 调整 `sp`、按需保存和恢复 `ra`、输出 `ret` |

在前面的加法示例中，前端已经用 `load` 和 `add` 表达了计算。后端再决定通过哪些 `lw`、`li`、`add`、`sw` 指令完成它，以及结果在栈中的具体位置。

当前后端主要把中间结果保存到栈，使用 `t0`、`t1` 等寄存器完成当前操作。完整的寄存器分配优化还没有实现。

### 对照刚完成的数组参数

源代码中的 `int a[][3]` 属于前端要理解的类型信息。前端根据 `a[1][2]` 生成 `getptr` 和 `getelemptr`：

```koopa
%row = getptr %base, 1
%elem = getelemptr %row, 2
```

这里假设 `%base` 的类型为 `*[i32, 3]`。后端再根据类型计算字节步长：第一步前进一行，即 12 字节；第二步前进两个整数，即 8 字节。

```text
前端负责：数组参数怎样表示，哪个下标用哪种 IR 指令。
后端负责：指针怎样装入寄存器，步长是多少字节，怎样用 mul/add 算出地址。
```

本项目的编译器输出到汇编为止。汇编、链接和执行由课程工具链继续完成，不在 `GenRiscV()` 内实现。

## 5. 为什么所有 AST 放在一起会让职责难以辨认

`BaseAst.h` 中至少包含以下几类内容：

| 内容 | 例子 | 职责 |
| --- | --- | --- |
| AST 节点字段 | `BinaryExpAst` 的左右操作数、`VarDefAst` 的名字与初值 | 描述源程序结构 |
| 编译上下文 | `ScopeStack()`、`FunctionTable()`、`LoopStack()` | 记录当前作用域、函数及循环环境 |
| 编译期处理与检查 | `Calc()`、`FillArrayInit()`、赋值合法性判断 | 求常量值、整理初始化结构、检查当前约束 |
| IR 构造与输出 | `Dump()`、`EmitBinary()`、`ArrayElementAddress()` | 把源程序行为翻译为 Koopa IR |

一个节点同时有“数据”和“生成 IR 的方法”，是当前实现的设计方式。它使按教程添加功能很直接，但随着符号、类型和控制流规则增多，文件承载的职责也变多了。

AST 是一种数据结构，前端是一个处理阶段；两者不是同一层概念。所有 AST 节点放在一个文件里，并不表示整个前端只有 AST 这一项工作。

## 6. 将来怎样拆分更容易理解

下面是后续重构方向，当前源码尚未按此布局迁移。

第一步可以先把 RISC-V 后端从 `main.cpp` 抽出。让 `main.cpp` 继续负责输入输出及阶段之间的调用，将 `GenRiscV()`、栈帧和加载辅助函数放进 `src/backend/riscv.cpp`，通过头文件提供后端入口。

第二步再分离 AST 的结构声明、符号上下文和 IR 生成实现。开始时可以保留各节点的 `Dump()` 接口，将其实现移出大头文件；如果后续需要独立语义分析或多种遍历方式，再调整遍历接口。

一个可能的布局是：

```text
src/
├── main.cpp                 编译流程入口
├── frontend/
│   ├── sysy.l               词法规则
│   ├── sysy.y               语法规则
│   ├── ast.h                AST 结构声明
│   ├── context.h            符号、作用域等上下文
│   └── irgen.cpp            AST 到 Koopa 的生成实现
└── backend/
    ├── riscv.h              后端入口声明
    └── riscv.cpp            Koopa 到 RISC-V
```

这些是文件与职责的拆分，不会自动产生一个优化中端。等真正实现 IR 分析和变换时，再增加对应模块。

每次迁移需要同步调整 include 和构建依赖，并运行现有回归验证行为；课程模板当前的构建方式也要一起核对。重构可以逐步完成，不要求一次改掉所有节点。

## 7. 阅读当前代码的顺序

1. 从 `main()` 看阶段之间如何连接，记下每次调用的输入和输出。
2. 选一个很小的 SysY 程序，在 `sysy.l` 和 `sysy.y` 中找到相应规则。
3. 找到规则创建的 AST 节点，看其字段保存了什么。
4. 沿 `Dump()` 和符号查询追踪生成的 Koopa 指令。
5. 在 `GenRiscV()` 中找到对应的指令分支，观察它怎样使用栈和寄存器。

阅读时可以反复记录三件事：当前处理的是哪种表示、依赖了哪些上下文、最后生成了什么。更多数组参数的实际 IR 与汇编见 [Lab9.3 复盘](labs/Lab9.3-进度与复盘.md)。
