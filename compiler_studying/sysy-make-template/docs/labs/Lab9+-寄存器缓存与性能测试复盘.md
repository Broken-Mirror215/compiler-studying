# Lab9+：寄存器缓存、地址计算与性能测试

记录日期：2026-10-03。本文对应本次代码中的基本块内寄存器缓存、常量数组下标化简和课程 `-perf` 模式。相关课程章节：[Lv9+ 总览](https://pku-minic.github.io/online-doc/#/lv9p-reincarnation/)、[寄存器分配](https://pku-minic.github.io/online-doc/#/lv9p-reincarnation/reg-alloc)、[代码优化](https://pku-minic.github.io/online-doc/#/lv9p-reincarnation/opt)、[性能测试](https://pku-minic.github.io/online-doc/#/lv9p-reincarnation/perf-testing)。

## 1. 今天先厘清的边界

当前编译器的前端把 SysY 生成 Koopa IR；后端在 `src/main.cpp` 中把 Koopa raw program 降为 RISC-V 汇编。今天的两项优化都发生在**后端生成汇编时**，没有修改 Koopa IR，也没有建立全局活跃区间或实现完整寄存器分配器。

| 问题 | 当前理解与做法 |
| --- | --- |
| 数组参数 `int a[][3]` 的两个下标如何移动指针？ | 第一次 `getptr` 跨一整行，步长为 `3 × 4 = 12` 字节；第二次 `getelemptr` 跨一个 `int`，步长为 4 字节。例如 `a[2][1]` 相对起始地址偏移 `2 × 12 + 1 × 4 = 28` 字节。 |
| 调用函数时能继续相信 `t` 寄存器里的值吗？ | `t0` 及本次缓存使用的 `t3`～`t5` 都是 caller-saved。后端在 `call` 前把缓存值写回它们原有的栈槽，后续使用再按栈槽读取。若某个值需要跨调用保留，调用方必须负责保存；不能假定被调用函数会保护 `t0`。 |
| 寄存器缓存与活跃区间有什么关系？ | 当前仅知道本基本块内最近存入缓存的 Koopa 计算结果。缓存淘汰时写回栈槽，不分析一个值的最后一次使用；跨基本块时也不沿控制流传播缓存状态。活跃区间分析是将来实现更完整寄存器分配的基础。 |

## 2. 基本块内寄存器缓存

实现位于 [`src/main.cpp`](../../src/main.cpp) 的 `LocalRegCache` 和 `GenRiscV()`：每进入一个基本块新建缓存，用 `t3`、`t4`、`t5` 保存二元运算结果。后续指令读取同一个 Koopa 值时，`Load()` 从缓存寄存器 `mv` 到所需目标寄存器；没有命中则走原来的 `LoadValue()`。三个位置都满时按轮换顺序淘汰，先用 `StoreStack()` 写回该结果原有栈槽，再放入新值。

写回是正确性的关键：二元运算结果起初只在缓存寄存器里，原有栈槽此时尚未更新。因此在 `call` 前和 `branch`、`jump` 前都执行 `Flush()`。对于分支，先把条件读进 `t0`，再写回缓存，最后发出跳转指令。`return` 后没有后继基本块，不需要为了后继读取写回。其他类型的结果仍按原有路径存栈；局部变量的 `alloc`、`load`、`store` 也没有改成寄存器常驻。

这是一种容易验证的局部复用策略，**不等于线性扫描寄存器分配**：没有给每个值求生存区间，没有基于最后使用位置释放寄存器，也没有跨基本块合并或全局溢出决策。

## 3. 常量下标的地址计算

`AddIndexToT0()` 复用于 `getptr` 和 `getelemptr`。先由指令的源指针类型确定步长，再按下标种类选择指令：

| 下标与字节偏移 | 生成方式 |
| --- | --- |
| 常量，偏移为 0 | 地址已经在 `t0`，不发出地址加法。 |
| 常量，偏移位于 `-2048`～`2047` | 一条 `addi t0, t0, 偏移`。RISC-V `addi` 的立即数为有符号 12 位。 |
| 动态下标，或常量偏移超出上述范围 | 保留原有的加载下标、`li` 步长、`mul`、`add` 路径。 |

例如 `int a[][3]` 的 `a[1][2]`，第一步按 12 字节跨行，第二步按 4 字节选元素。优化改变的是地址计算指令，不改变 `getptr` 与 `getelemptr` 的类型和步长语义。用 `tests/array-param/chain.c` 检查过常量下标汇编中的 `addi`，用 `tests/array-init/nd_read_write.c` 检查过动态下标仍走乘法路径。

## 4. 测试与测量

在课程容器中构建并运行：

```bash
make -j2
python3 scripts/test.py --mode riscv
autotest -perf -s perf .
```

| 检查 | 结果 |
| --- | --- |
| 构建 | `make -j2` 成功 |
| RISC-V 功能回归 | 自定义用例 19/19、Lv8 12/12、Lv9 22/22，共 53/53 |
| `-perf` 接口 | 与 `-riscv` 编译同一输入，输出汇编逐字节一致 |
| 课程性能用例 | `PASSED (20/20)` |

入口现在接受 `compiler -perf 输入文件 -o 输出文件`，与 `-riscv` 一样输出 RISC-V 汇编。命令行参数在读入源文件前检查；`-koopa` 仍输出 Koopa IR。

课程 `autotest` 的这 20 个用例全部显示 `time elapsed: 0H-0M-0S-0us`。因此，这个字段只能说明当前环境下未取得可用耗时，**不能据此判断优化速度**。为得到一组可比较的数据，另取性能用例 `00_bitset1.c`，用本次修改前的 Git 提交 `243574e` 的源码编译旧版编译器，再分别用旧版和当前编译器生成 RV32 可执行文件。在同一容器、同一输入 `10000000 197123` 下，通过 QEMU 交替运行各 3 次；两版程序退出成功，标准输出哈希相同。记录进程外部墙钟时间如下：

| 版本 | 三次墙钟时间 | 中位数 |
| --- | --- | --- |
| 修改前 | 4.983、4.954、4.950 秒 | 4.954 秒 |
| 当前版本 | 4.671、4.736、4.721 秒 | 4.721 秒 |

这个单一用例中，当前版本的中位墙钟时间比修改前低约 **4.7%**。同一用例的静态汇编计数也从 `mul` 82 条降至 24 条，`lw`/`sw` 合计从 481 条降至 430 条。静态条数并不等于动态执行次数；墙钟时间也包含 QEMU 与进程环境开销。这组数据只能说明**此用例、此环境、这两项改动合在一起**的表现，不能分离寄存器缓存和下标化简各自的收益，也不能推断整套性能测试的提速比例。

## 5. 后续学习方向

下一步可以先为 Koopa 值统计基本块内的最后使用位置，使缓存能在值不再使用时释放寄存器；再考虑跨基本块活跃性和调用点处理。引入全局寄存器分配时，需要明确输入表示、控制流和定义—使用关系，再选择线性扫描或图着色等算法。每次修改都用功能回归、优化前后汇编和可用的运行时间一起验证。
