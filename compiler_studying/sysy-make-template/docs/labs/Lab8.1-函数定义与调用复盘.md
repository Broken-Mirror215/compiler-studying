## 2. 用同一个例子贯穿各层

```c
int half(int x) {
    return x / 2;
}

int main() {
    return half(10);
}
```

主线是：源代码 → lexer 返回 token → parser 建 AST → AST 的 Dump 生成 Koopa 文本 → libkoopa 解析成 raw IR → GenRiscV 生成汇编 → 汇编、链接、执行。

当前项目的 `Dump()` 已主要负责 IR 生成，不是单纯打印 AST。有些 Dump 输出指令，有些只设置 `result`，读代码时必须看具体实现。

## 3. 语法规则怎样组装 AST

位置：`src/sysy.l`、`src/sysy.y`。

- lexer 增加 `void` 关键字。
- `CompUnit : FuncDef` 创建函数列表；`CompUnit : CompUnit FuncDef` 取出已有列表并追加函数。这是左递归规则积累元素。
- `Program : CompUnit` 把根节点交给 main 中的 `ast`。
- `FuncDef` 保存返回类型、名字、形参名字和函数体。
- `UnaryExp` 中的调用规则创建 `FuncCallAst`，保存函数名及实参表达式树。

`$1`、`$2` 是右侧相应符号的语义值，`$$` 是本次归约得到的语义值。`$$ = node` 只是把节点向上一层语法规则传递，不是在执行 SysY 函数，也没有生成 IR。

### 形参和实参为什么用不同容器

```c
int add(int x, int y) { return x + y; } // 形参 x、y
add(1 + 2, a * 3);                     // 实参是两个表达式
```

| 数据 | 当前表示 | 原因 |
| --- | --- | --- |
| 形参列表 | `vector<string>` | 当前都是 int，只需额外保存名字 |
| 实参列表 | `vector<unique_ptr<BaseAst>>` | 表达式需要保留树，之后才能生成求值指令 |

`FuncFParam : INT IDENT { $$ = $2; }` 传递的是名字字符串指针，不是函数运行时的返回值。到数组参数阶段，形参信息还需要扩展。

### “中转站”与所有权

`FuncFParamsAst`、`FuncRParamsAst` 是解析列表时的临时载体，自身不生成 IR。

```cpp
auto args = unique_ptr<FuncRParamsAst>(
    static_cast<FuncRParamsAst *>($3)
);
node->args = move(args->args);
```

1. `static_cast` 根据该语法规则实际创建的类型，把基类指针转回具体类型。
2. `unique_ptr` 接管临时载体的生命周期。
3. `move` 将列表转入最终调用节点，表达式节点的所有权随之转移。
4. 动作结束后临时载体销毁，最终节点仍持有表达式树。

`block.get()` 则只取出原始指针，不转移所有权。基类虚析构函数保证通过 `unique_ptr<BaseAst>` 销毁派生对象时，派生对象也能正确析构。

## 4. 函数定义如何生成 IR

位置：`AST/BaseAst.h` 中的 `FuncDefAst::Dump()`。

### 返回类型

`FuncTypeAst::Dump()` 设置 `result`：int 对应 `": i32"`，void 对应空字符串。函数节点再把它拼到函数头。这个 Dump 不直接输出指令。

### 先登记函数，再生成函数体

`FunctionTable()` 保存函数名对应的 `is_void` 和 `param_count`。

- `CompUnitAst::Dump()` 在处理整个程序前清空表。
- `FuncDefAst::Dump()` 在处理当前函数体前登记当前函数。
- 因为先登记再进入函数体，自递归调用能查到当前函数。
- 当前按源码顺序登记，没有预扫描全部后续函数。

这张表服务于调用检查及返回值处理；变量和常量仍放在 `ScopeStack()` 中。当前分表设计不等于完整的统一名字解析和类型检查。

### 形参从“名字”变成“可读写变量”

```koopa
fun @half(@x: i32): i32 {
%entry:
  %var_x_0 = alloc i32
  store @x, %var_x_0
  %0 = load %var_x_0
  %1 = div %0, 2
  ret %1
}
```

| 名字 | 含义 |
| --- | --- |
| 源代码中的 `x` | 查符号表时使用的名字 |
| IR 中的 `@x` | 函数接收到的参数值 |
| `%var_x_0` | 保存参数值的局部内存地址 |

仅输出函数头不会登记变量。必须生成 alloc/store，并把 `x → Variable, addr=%var_x_0` 加入符号表，已有的 `LValAst` 才能生成 load；赋值也能复用原来的 store 逻辑。

### 为什么拆出 DumpInCurrentScope

形参和函数体最外层局部变量共享一个作用域：

```c
int f(int x) { int x = 2; return x; }     // 同层重名，应拒绝
int f(int x) { { int x = 2; } return x; } // 内层可以遮蔽，退出后仍访问形参
```

所以函数节点 EnterScope 后登记形参，再调用函数体的 `DumpInCurrentScope()`。普通嵌套块仍调用 `BlockAst::Dump()`，由它自行 EnterScope/ExitScope。

`FuncDefAst::Dump()` 的实现移到 `BlockAst` 定义后，是为了调用已完整定义的 `BlockAst` 方法；类内仍保留声明。头文件中的这份类外定义使用 inline，避免多个翻译单元包含头文件时造成重复定义。

## 5. 调用节点如何生成 IR

位置：`FuncCallAst::Dump()`。

顺序为：查函数表 → 检查参数数量 → 生成每个实参的求值指令 → 收集结果名字 → 输出完整 call。

```c
half(3 + 7)
```

生成：

```koopa
%2 = add 3, 7
%3 = call @half(%2)
```

不能先输出 `call @half(` 再执行实参 Dump，否则实参的 add/load/call 指令会插到这行中间。

int 调用分配临时结果名字，并把它放进调用节点的 `result`；void 调用不写 `%n =`，并清空 `result`。外层 return、加法或其他调用通过子节点的 result 使用计算结果。

实参本身是一次 void 调用时，空 result 会触发检查。当前这不是完整的表达式类型系统，不能据此宣称所有 void 误用都已被提前诊断。

## 6. void 返回与终结状态

`StmtAst` 有表达式时生成 `ret 值`，无表达式时生成 `ret`。

函数体结束后，仅当函数为 void 且 `!body->IsTerminated()` 时补 `ret`。不能无条件追加，因为同一基本块在终结指令后不能再放指令。

`if (x) return;` 仍有未返回的路径，结束块需要补 ret；if/else 两边都返回时则不再补。

后端 `KOOPA_RVT_RETURN` 中，空返回值是合法情况，不能保留旧的 `assert(ret_value)`。只有返回值存在才加载到 a0，但恢复 ra（需要时）、恢复 sp 和 ret 都照常执行。

## 7. 形参在 RISC-V 中从哪里来

位置：`src/main.cpp` 的 `LoadValue()`。

普通指令结果从 `frame.offsets` 对应的栈位置读取；整数使用 li；`KOOPA_RVT_FUNC_ARG_REF` 根据参数下标读取。

- 下标 0–7：从 a0–a7 读取。
- 下标 8 及之后：从 `当前 sp + frame.size + (index - 8) * 4` 读取。

为什么加 frame.size？调用者把第九个参数放在调用时的 sp+0。被调用者进入后执行 `sp -= frame.size`，同一地址就变成它当前的 sp+frame.size。

函数入口的 store 会立刻把传入参数存到自己的局部栈空间。后面的调用即使覆盖 a0–a7，也不会破坏已经保存的形参。

## 8. 栈帧为什么扫描两遍

位置：`StackFrame`、`BuildStackFrame()`。

| 字段 | 用途 |
| --- | --- |
| offsets | 局部变量及有结果指令在栈中的偏移 |
| outgoing_size | 调用其他函数时，超出八个的实参空间 |
| has_call | 当前函数是否含 call |
| ra_offset | 保存当前函数返回地址的位置 |
| size | 整个栈帧大小，向上对齐到 16 字节 |

第一遍扫描所有 call，记录 has_call，并计算最大的额外传参空间。第二遍从 outgoing_size 后面开始，为非 unit 指令分配位置。

```text
A = 所有调用中 max(参数数量 - 8, 0) 的最大值 × 4
S = 当前实现中局部变量及指令结果所需空间
R = 有 call 时为 4，否则为 0
size = align_up(A + S + R, 16)
ra_offset = size - 4（有 call 时）
```

传参空间取最大值，因为多次调用复用同一空间。递归进入另一次函数调用时，会建立新的栈帧。

void call 虽然没有结果，仍然会修改 ra，也可能有超过八个参数；不能在第一遍因为它是 unit 就跳过。

这里每个非 unit 指令只预留 4 字节，是当前标量阶段的实现；将来数组的 alloc 大小需要重新处理。

## 9. ra 保存、调用和返回怎样配合

`call half` 会把返回到调用点后面的地址写入 ra。因此 main 在调用 half 前，要保护进入 main 时的原始 ra。

```asm
main:
  addi sp, sp, -16
  sw ra, 12(sp)

  li a0, 10
  call half
  sw a0, 0(sp)

  lw a0, 0(sp)
  lw ra, 12(sp)
  addi sp, sp, 16
  ret
```

入口必须先调整 sp，再按 ra_offset 保存；出口必须先读取 ra，再恢复 sp。两次访问 ra 时必须使用相同的栈帧基址。

`KOOPA_RVT_CALL` 做三件事：

1. 前八个实参放入 a0–a7，之后的实参写到当前 sp+0、sp+4 等位置。
2. 去掉 Koopa 函数名开头的 @，输出 `call 函数名`。
3. 若有返回值，立即将 a0 保存到该 call 指令的结果槽；后续调用会覆盖 a0。

当前 AST 先求完所有实参，再输出外层 call；参数在入口已存栈，表达式结果也存栈，这些设计共同使嵌套调用可以逐个装载参数。

| 错误 | 原因与正确写法 |
| --- | --- |
| 分隔参数用 `i >= 0` | size_t 非负，条件恒真；用 `i > 0` |

## 12. 十个问题的参考答案

### 1. 形参为什么只存名字，实参为什么要存 AST？

形参描述函数接收什么，实参描述调用时要计算什么。

```c
int add(int x, int y) { return x + y; }
// 调用处：
add(1 + 2, a * 3);
```

当前阶段的形参类型固定为 int，因此保存 `x`、`y` 两个名字，就能恢复参数数量、顺序和类型。并不是形参永远只需要名字；数组参数出现后，还要保存类型、维度等信息。

实参则可以是任意受支持的表达式。`1 + 2` 和 `a * 3` 要保存操作符及子表达式，之后才能生成计算指令，所以使用表达式 AST。即使一个实参只是 `10`，它也通过 NumberAst 统一参与这套流程。

注意：实参 AST 存的是“如何计算”，不是函数运行时已经算好的数值。当前 Dump 通常生成运行时求值的 IR，并用 result 记录结果名字；常量表达式的 Calc 是另一条处理路径。

### 2. move 和 get 分别会不会转移所有权？

严格来说，`std::move` 本身只把表达式转换为可以被移动的形式；实际转移发生在随后调用的移动构造或移动赋值中。

```cpp
node->args = std::move(args->args);
```

这里 vector 的移动赋值把实参列表转给最终节点，其中 unique_ptr 管理的 AST 随列表转移。临时列表载体销毁时，不会把已转移的子树删除。被移动的容器仍然有效，但一般不应依赖它具体还保留什么内容。

```cpp
auto *body = static_cast<BlockAst *>(block.get());
```

`get()` 只提供一个非拥有的原始指针，所有权仍属于 block。不能因此手动 delete body，也不能再用另一个 unique_ptr 接管 body，否则可能重复释放。block 销毁后，body 也不能继续使用。

`static_cast` 只改变这里使用的指针类型，不创建新对象，也不转移所有权；其正确性依赖于我们知道原节点确实是 BlockAst。

### 3. 为什么 `@x` 还要 store 到局部地址？符号表记录的是什么？

`@x` 是传进函数的值，局部地址是可读写的存储位置。SysY 中形参可以被赋值：

```c
int f(int x) {
    x = x + 1;
    return x;
}
```

当前编译器把可修改变量统一表示为内存，因此入口生成：

```koopa
%var_x_0 = alloc i32
store @x, %var_x_0
```

以后读 x 就 load，写 x 就 store。符号表登记的是源代码名字 `x` 对应的 `SymbolInfo{Variable, 0, "%var_x_0"}`；这里 0 是未使用的常量值字段，不是说参数值为 0，也不是栈偏移。

IR 地址如何对应机器栈偏移，是后端 frame.offsets 的工作。前端符号表和后端栈偏移表不是同一张表。

对于不修改参数的简单程序，直接使用传入的 IR 值也可以。当前选择先存入局部内存，是为了复用变量读写逻辑，并在后端入口及时保存参数寄存器中的值。

### 4. 为什么形参登记后不能直接让函数体再 EnterScope？

原因是形参和函数体最外层局部声明处在同一个作用域，必须一起做重名检查。

```c
int f(int x) {
    int x = 2;  // 应被判定为同层重复定义
    return x;
}
```

如果登记形参后直接调用会 EnterScope 的 BlockAst::Dump，就多出一层表。VarDefAst 只检查当前层是否重名，于是会错误地允许这个局部 x 遮蔽形参。

这不是“多一层就找不到形参”：LookupSymbol 从内到外查找，通常仍找得到。真正的问题是作用域层次与语言规则不一致，导致重名检查失效。

所以函数体最外层使用 DumpInCurrentScope；真正的嵌套 `{ ... }` 才通过 Dump 创建新作用域，允许内层同名变量在块内遮蔽形参。

### 5. 为什么必须先求实参，再打印 call？

在当前通过 cout 拼接 IR 的实现中，实参 Dump 可能输出一整串指令，甚至输出分支和基本块。因此必须先让这些指令完整生成，再输出使用结果的 call。

```c
half(3 + 7)
```

正确顺序：

```koopa
%0 = add 3, 7
%1 = call @half(%0)
```

如果先打印 `call @half(`，再执行参数 Dump，add 会插进 call 的文本中间，直接破坏语法。即使改用结构化的 IR 构建器，也仍须让被调用函数使用的实参值在调用前准备好。

对于 `add(f(), g())`，当前实现先生成 f 的调用及结果，再生成 g 的调用及结果，最后生成 add 的调用。保存到 values 里的是 IR 操作数名字，不是机器寄存器名字；后端再决定怎样把这些值放到 a0、a1。

### 6. 为什么第九个参数写入时是 sp+0，读取时却加 frame.size？

地址没有变，变化的是被调用者的 sp。

假设调用前调用者的 sp 是 1000，第九个参数就写到地址 1000。被调用者的栈帧大小是 48，它进入后令 sp 变为 952：

```text
调用者写入：1000 + 0 = 1000
被调用者读取：952 + 48 + 0 = 1000
```

所以被调用者的读取公式是：

```cpp
frame.size + (index - 8) * 4
```

这里 frame.size 属于被调用者，不是调用者。第十个参数再加 4，以此类推。sp 是寄存器，不是每个函数各有一个独立的 sp；函数通过调整它建立自己的栈帧，返回时再恢复。

### 7. outgoing_size 为什么取最大值？void call 为什么也要统计？

当前函数每次实际执行一个调用，同一片传参区在调用完成后可以复用，因此只需要容纳参数最多的那个调用。

调用十参数函数需要 8 字节，调用十二参数函数需要 16 字节，预留 16 字节足够，无需相加成 24 字节。即使源代码有嵌套调用，当前 IR 也先算内层调用，再准备外层调用；内层返回值保存在独立的结果槽中。

递归也不要求在一个栈帧中累加所有层的空间：每次递归进入都会新建栈帧，各自拥有传参区和局部数据。

void 只说明“没有返回值”。它仍可能接收十二个参数，也仍会通过 call 改写 ra，所以必须统计它的传参空间和 has_call。只有分配“调用结果槽”时，才因其结果类型为 unit 而跳过。

### 8. call 修改了哪个寄存器？为什么需要保护它？

函数调用需要把“调用结束后从哪条指令继续”写入 ra。假设调用链为 `启动代码 → main → half`：

- 进入 main 时，ra 指向启动代码中 main 调用后的继续位置。
- main 调用 half 时，ra 被更新为 main 内部 call 后的继续位置。
- half 执行 ret，利用这个地址回到 main。
- main 自己返回前，需要恢复原来指向启动代码的地址。

因此当前实现对含 call 的函数，在入口保存原 ra，在每条返回路径恢复它。递归中每层栈帧保存自己的 ra，返回时才能逐层退回。

还要区分 call 指令本身建立返回地址，以及被调用函数执行时可能改写的寄存器。a0–a7、t0–t6 等不能指望跨调用保持原值；当前将需保留的数据存栈，避免依赖这些寄存器跨调用存活。

### 9. 为什么调用返回后立刻把 a0 存栈？

a0 是约定的整数返回值位置，同时还是下一次调用的第一个参数寄存器。下一次传参或调用都可能覆盖它。

```c
return f() + g();
```

f 返回后如果只把结果留在 a0，g 返回时 a0 就变成 g 的结果，f 的结果丢失。因此当前后端这样处理：

```asm
call f
sw a0, F(sp)
call g
sw a0, G(sp)
# 再从两个不同槽位读取，执行加法
```

这里 F、G 只是示意不同偏移，不是实际输出中的符号。具体位置来自 frame.offsets 中两个 call 指令各自的条目。

“立即存栈”是当前把所有计算结果放栈上的实现策略，并非所有编译器都必须如此。更复杂的后端也可以用合适的寄存器保存，但必须保证后续操作不会破坏仍需使用的值。

### 10. 如何判断失败在哪一阶段？

沿最小输入逐层检查，找到第一个不满足约定的输出；不要看到错误就同时修改前后端。

| 阶段 | 看什么 | 本实验中的典型问题 |
| --- | --- | --- |
| 编译器自身构建 | make 的错误、报错文件与行号 | next_offset 重复声明，程序还没机会处理 SysY |
| 词法/语法与 AST 构造 | yyparse 是否成功，规则是否建出正确节点 | 调用规则缺失、实参没有放入 args |
| AST 遍历与 IR 生成 | Dump 是否抛异常，ir_stream 中的文本是否完整 | x 未登记、函数未定义、漏打印调用右括号 |
| Koopa 验证 | koopa_parse_from_string 的错误 | void 函数末尾缺 ret、返回值类型不匹配 |
| RISC-V 生成 | 指令分支、偏移查找、输出汇编 | 不支持 CALL、参数被当成普通栈结果查找 |
| 汇编和链接 | 汇编器、链接器的具体报错 | 指令格式错误、目标函数符号缺失 |
| 程序执行 | 返回值、输出、是否超时，结合调用前后寄存器与栈 | 未恢复 ra、栈参数偏移错误、调用结果被覆盖 |

当前 main 先把 IR 收集到 ir_stream，再用 libkoopa 验证，验证成功后才输出目标文件。因此 IR 验证失败时，`-o` 文件可能尚未创建，不能直接拿以前遗留的同名文件判断本次输出。

定位时必要的话，可以临时把 `ir_stream.str()` 输出到 cerr，或用调试器查看 AST 字段和生成的 IR；不要往正式 IR/汇编输出里混入调试文字。修改源码后一定重新构建，再用新的编译器复现。

最后要区分“汇编生成成功”和“程序执行正确”：half(10) 的汇编能被接受，还要实际运行得到 5，才验证了这条路径的执行结果。
