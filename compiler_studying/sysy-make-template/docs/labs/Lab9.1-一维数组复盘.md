## 1. 这次到底完成了什么

| 功能 | 当前行为 |
| --- | --- |
| `int a[3];` | 局部数组只分配空间；全局数组零初始化 |
| `int a[3] = {};` | 三个元素全部初始化为零 |
| `int a[3] = {5};` | 第一个元素为 5，后两个补零 |
| 局部变量数组初值 | 可以是运行时表达式，包括函数调用 |

| 同名数组位于不同作用域 | 符号查找从最内层向外，生成的存储名字各不相同 |

这里的“补零”有前提：存在初始化列表。局部 `int a[3];` 不主动生成三个 `store 0`，而局部 `int a[3] = {};` 会全部写零。全局没有显式初始化的数组则使用 `zeroinit`。

## 2. 用一个例子串起整条编译流程

```c
const int base = 2;   //编译期计算

const int global[3] = {base, base + 1};//这个是什么？

int main() {
  const int local[3] = {base, base + 1};
  return local[0] + local[1] + global[2];
}
```

编译流程是：源代码 → 词法 token → Bison 归约构造 AST → AST 的 `Dump()` 生成 Koopa 文本 → libkoopa 解析为 raw IR → `GenRiscV()` 生成汇编 → 汇编、链接、执行。

`base` 是整数常量，符号表直接记录值 2，它没有独立存储空间。`global` 和 `local` 是常量数组，仍然需要存储空间。它们的元素初值都先计算为 `{2, 3, 0}`，运行时再按地址读取。这个程序返回 5。

//这个
当前 `Dump()` 已负责 IR 生成，而非单纯打印 AST。`Calc()` 则负责编译期求值。两者不能互换：局部变量数组的初值可能需要 `Dump()` 执行表达式，常量数组的初值必须用 `Calc()` 得到整数。

## 3. 长度为什么还要保存为 AST 节点

位置：`AST/BaseAst.h` 中的 `VarDefAst`、`ConstDefAst`，以及 `src/sysy.y`。

`array_len` 是 `unique_ptr<BaseAst>`，不是因为已经在为二维数组存第二个长度，而是因为源代码中的长度可以是一个表达式：

```c
const int n = 2;
int a[n + 1];
```

parser 归约数组定义时拿到的是表示 `n + 1` 的表达式树。此时只负责组装树，不直接把整棵树替换成整数。定义节点生成 IR 时调用 `array_len->Calc()`，再通过符号表查到 `n`，得到长度 3。

如果一开始只保存 `int`，就需要在解析阶段提前做符号查找和求值，会把语法分析与后续语义处理混在一起。当前保存表达式树的方式与已有常量表达式实现一致。

## 4. 初始化列表怎样进入 AST

`ArrayInitAst` 保存 `vector<unique_ptr<BaseAst>> elems`。这是“一串初值表达式节点”，还不是已经算好的整数数组。

`InitValList` 用 `Exp` 收集变量数组初值；`ConstInitValList` 用 `ConstExp` 收集常量数组初值。左递归列表每次取出已有列表，再把新节点追加进去。`{}` 创建一个元素列表为空的 `ArrayInitAst`。

常量数组定义规则的右侧是：

```text
IDENT '[' ConstExp ']' '=' ConstInitVal
  $1           $3              $6
```

因此 `$3` 交给 `array_len`，`$6` 交给 `init`。`reset($3)` 和 `reset($6)` 是把 parser 创建的节点交给 `unique_ptr` 管理，不是在复制节点，也没有计算表达式。

`ArrayInitAst::Dump()` 本身会抛出异常，因为它不知道数组总长度、局部还是全局，以及初值是否需要常量求值。真正处理初始化列表的是 `VarDefAst` 或 `ConstDefAst`。

## 5. 变量数组与常量数组的四条生成路径

### 局部变量数组

定义节点计算长度，输出 `alloc [i32, len]`，并在当前符号表记录数组地址。若有初始化列表，逐元素调用表达式的 `Dump()`，拿到 `result`，再输出 `getelemptr` 和 `store`。缺少的元素使用字符串 `"0"`。

```c
int a[3] = {getint(), 5};
```

第一个元素要在运行时调用 `getint()`，因此不能对它使用 `Calc()`。生成的程序先执行调用，再把调用结果存入第一个元素。

### 全局变量数组

全局作用域不能使用普通指令逐个 `store`，所以初值必须在编译期确定。输出形式为：

```koopa
global @a = alloc [i32, 3], {5, 0, 0}
```

右侧聚合常量必须包含全部三个元素。不能只输出 `{5}`，因为 Koopa 根据元素数量推导初始化类型，它会变成 `[i32, 1]`，与分配的 `[i32, 3]` 不匹配。没有显式初值时使用 `zeroinit`。

### 局部常量数组

`ConstDefAst` 先建立 `vector<int> values(len, 0)`，再对列表中的每个表达式调用 `Calc()`。这样显式元素计算完成，缺少的元素已经是零。

随后分配局部数组，用 `getelemptr` 定位每个元素，并将 `values[i]` 存进去。这里的 `vector<int>` 只是定义节点生成 IR 时的临时数据，并没有把整份常量数组加入符号表。

### 全局常量数组

初值计算方式与局部常量数组相同，但输出的是全局聚合常量。符号表记录 `ConstArray` 和地址，供后续读取和禁止赋值使用。

本项目使用 `alloc` 来表示常量数组的存储，生成到普通数据段。源语言的“不能修改”由前端检查保证；目前没有额外把它放入只读段。

## 6. 地址和元素值是两个不同结果

位置：`LValAst::Address()`、`LValAst::Dump()`、`AssignStmtAst::Dump()`。

```koopa
%a = alloc [i32, 3]
%p = getelemptr %a, 1
%v = load %p
```

`%a` 是指向整块数组的指针，类型为 `*[i32, 3]`；`%p` 是第二个元素的地址，类型为 `*i32`；`%v` 才是元素里保存的整数，类型为 `i32`。

`Address()` 负责生成 `%p` 并返回它的名字。读取表达式由 `Dump()` 再生成 `load`；赋值语句则直接把右侧值 `store` 到这个地址。`getelemptr` 本身没有读取数组元素，也没有修改数组元素。

`Address(bool for_write = false)` 将读写需求传进来：读取允许 `Array` 和 `ConstArray`，赋值调用 `Address(true)`，遇到 `ConstArray` 立即报错。初始化常量数组时的 `store` 直接由定义节点生成，不走后续赋值语句的检查。

`LValAst::Calc()` 仍拒绝带下标的数组元素。按本节教程的边界，`const int x = a[0];` 不要求从常量数组中折叠出值。普通运行时 `return a[0];` 则可以读取常量数组。

## 7. RISC-V 后端怎样接住数组

位置：`src/main.cpp`。

### 空间大小与栈帧

`TypeSize()` 返回整数和 RV32 指针的大小 4；数组大小递归计算为元素数量乘以元素类型大小。因此 `[i32, 3]` 需要 12 字节。

`alloc` 返回的是指针，但局部数组对象本身需要 12 字节。`BuildStackFrame()` 对 `alloc` 使用其指向类型的大小；对普通指令结果仍预留 4 字节。例如 `getelemptr` 产生的地址是一个 4 字节的指针结果，而不是又生成了一个 12 字节数组。

### 计算元素地址

`getelemptr` 的地址计算是：

```text
元素地址 = 数组起始地址 + 下标 × 元素大小
```

当前后端取起始地址到 `t0`，取下标到 `t1`，取元素大小到 `t2`，执行乘法和加法，再把指针结果保存到其栈槽。对于一维整数数组，步长是 4。

`LoadAddress()` 按地址来源处理：全局 `alloc` 使用 `la`；局部 `alloc` 计算 `sp + offset`；`getelemptr` 则从其结果栈槽取出保存的指针。随后 `load` 用 `lw` 读指针指向的内存，`store` 用 `sw` 写入。

较大的局部数组会让栈帧和访问偏移超过 `addi` 的立即数范围。当前地址及栈访问辅助函数已有大偏移处理，不能只把所有偏移硬塞进一条 `addi`。

### 全局初始化

`EmitGlobalInit()` 处理三类数据：整数输出 `.word`，`zeroinit` 输出 `.zero TypeSize(...)`，聚合初始化则逐个递归处理元素。

例如 `{5, 0, 0}` 对应三条 `.word`；未初始化的三个整数对应 `.zero 12`。这些是汇编器的数据指令，不是程序运行时执行的三条存储指令。

8.3 已经负责全局对象、符号和数据段；9.1 扩大了全局对象的类型及初始化形式。原先只需保存一个整数，现在还要保存数组、聚合常量和整块零初始化。

## 9. 本次手写错误与修正理由

| 错误 | 后果 | 修正 |
| --- | --- | --- |
| `ArrayInitAst` 定义在 `ConstDefAst` 后面 | 使用它的 `dynamic_cast` 时类型尚未定义，C++ 构建失败 | 将完整类定义移到使用处前面；仅前置声明不能支持这里的类型转换和成员访问 |
| 输出 `alloc i32[,` | C++ 可以编译，但生成的 Koopa 文本语法错误 | 改为 `alloc [i32,` |
| `getelemptr` 后缺空格 | 操作码与地址名字粘在一起 | 输出 `getelemptr ` |
| 使用 `ptr` 作为当前初始化下标 | 当前指针结果被误当成下标，形成错误的 IR 定义与类型 | 使用循环整数 `i` |
| 初始化只计算地址，没有 `store` | 数组空间未被写入期望值 | 补上 `store values[i], ptr` |
| 读取检查只允许 `Array` | 常量数组即使定义成功也无法读取 | 同时允许 `ConstArray`，写入另行检查 |
| parser 仍只有整数常量定义 | 合法的 `const int a[3] = {...}` 无法进入新 AST 分支 | 添加数组定义、常量初始化列表及 `%type` |

这说明验证要分层：C++ 构建通过只证明实现能编译；Koopa 文本能解析还不能证明初始化语义正确；运行结果正确才能覆盖这些读写行为。不能用旧的 `build/compiler` 成功执行来代替对新代码的重新构建。
